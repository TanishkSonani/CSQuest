# VM browser and terminal

Administrators open **Library → Boot storage** and click **Firefox** or **Terminal**. Each launcher opens its own tab and asks for the current CSQuest password before starting a VM process. Opening Library never starts either application. Both applications can run if explicitly launched, but neither is automatically started with the other. There is one active session per application across administrators.

Firefox is installed natively for ARM64 under `/opt/csquest-remote/firefox` on the Boot filesystem. Launchers are virtual applications, not downloadable Library inventory files, and do not appear in public shares or learner views. Firefox's first launch presents Mozilla's own welcome/terms screen for the user to review. Browsing runs on the VM. The terminal is an actual Bash PTY on the VM, served by ttyd's xterm.js client, under `csquest-terminal`; it has no sudo privileges and cannot read platform/database/SSH secrets. Administrative VM maintenance still uses the existing SSH workflow.

Normal tab closure sends an explicit stop request for the entire session control group, including child/background processes. Firefox transport interruptions can reconnect to the same VM process for up to 90 seconds. If a browser crashes, the network disappears or the stop request cannot arrive, the broker expires its lease after 90 seconds (checked every five seconds). A four-hour hard session limit is also enforced. Exact instantaneous detection of an unclean client disconnect is not possible. Firefox's local profile/downloads and terminal home persist; ending the VM process does not promise logout from every website. These are shared application homes for trusted platform administrators, not separate private desktops for multiple users.

## Installation and boundaries

From a reviewed checkout on the ARM64 Ubuntu VM, run `sudo bash deploy/configure-remote.sh`, followed by `sudo bash deploy/configure-remote-proxy.sh`. Set `REMOTE_SESSION_SOCKET=/run/csquest-remote/broker.sock` in the existing ignored application `.env`, preserving other variables. Restart/deploy the application normally. The proxy script backs up Nginx configuration, validates it and reloads with rollback on failure. No VNC or terminal port is exposed publicly.

The root-owned broker has a Unix socket accessible only to root and the CSQuest service group. Its API only accepts Firefox/Terminal launch, inspect, attach, lease and stop operations; it never accepts a shell command, arbitrary executable, filesystem path or systemd properties. Browser and terminal programs execute as distinct non-root users. Application authentication, administrator authorization, current-password verification, CSRF/Origin validation and login-session ownership are enforced before access. WebSockets recheck login/admin permissions every ten seconds. Duplicate connections cannot terminate the original session.

Both applications together use `csquest-remote.slice`, capped at two CPU cores and 5 GB RAM, with lower CPU scheduling weight than the platform and a 20 ms CPU quota period; Firefox has a 4 GB / 2,048-task limit and Terminal a 1 GB / 256-task limit. The combined slice allows 2,560 tasks. They cannot modify the system filesystem or platform data, have isolated temporary storage, and terminate when the broker stops. Dedicated UID firewall rules block new connections to private/loopback services and OCI metadata, while retaining established VNC/terminal replies and system DNS. The CSQuest service's existing Object Storage instance-principal access is unaffected. Read-only host system information in `/proc` is available to both applications, while other users' processes are hidden. Host services, code and user home directories remain protected; remote programs are not run as root.

Persistent homes use bounded sparse ext4 images on Boot: 2 GB for Firefox and 1 GB for Terminal, with Firefox disk cache limited to 128 MB. Their actual host disk consumption and installed binaries count as system/other usage in Library's filesystem accounting. Library allocations are unchanged. File downloads inside Firefox stay on the VM; an automatic import/export bridge to Library is not implemented.

Firefox security updates are checked every six hours by `csquest-remote-update.timer`. The updater skips active sessions and atomically excludes launches during replacement. The previous browser build is retained. `sudo csquest-update-firefox` forces manual maintenance and stops remote sessions; ordinary OS packages use the VM's normal package updates. Broker/worker changes are applied by rerunning the reviewed installer and restarting the broker during maintenance; they are root-owned and are not executed directly from the application-owned deployment checkout.

Remote browsing does not make activity invisible to network monitoring or authorize access prohibited by organizational policy. The client needs HTTPS/WebSockets to CSQuest; sites are requested from the VM's network connection. Basic VNC does not provide an audio stream or microphone/camera forwarding.

## Validation

`tests/remote-sessions.test.mjs` covers administrator/password/origin gates, session binding, duplicate connection safety, WebSocket relay, close cleanup and vendor asset restrictions. `tests/remote-sessions-browser.cjs` covers Boot launchers, independent new-tab launch, noVNC protocol connection, desktop/mobile bounds and tab-close cleanup using an isolated test database and simulated desktop.

The actual VM was also tested through a private loopback preview and SSH tunnel: native Firefox rendered in noVNC; ttyd accepted `id -un` and `uname -m` and wrote a QA marker under the terminal home; closing each tab removed its session service. The temporary QA account, preview and marker were removed afterward. This validates the remote feature without checking the deployment pipeline. Screenshots are ignored local artifacts under `qa-results/remote`.

Final local regression: 224 tests passed, two optional tests skipped; the focused authorization/session test also passed after adding same-administrator/different-login rejection. Course validation passed. Real VM Firefox used approximately 355 MB at its welcome screen under the verified 3 GB cap. A disconnected Firefox session expired and its complete service was removed without client heartbeats. These are functional checks, not a heavy-browsing performance benchmark.

## Linux terminal workspace

New terminals start at the real VM filesystem root (`/`), so `ls` shows the normal Linux directories. The Bash prompt identifies the Linux user, VM hostname and current path. Use `cd ~/linux-practice` for persistent exercises; `documents`, `scripts`, `notes` and a getting-started README are created without replacing existing files. History, standard completion and optional user `~/.bashrc` settings persist. System-wide `/proc` information is readable for commands such as `free` and `lscpu`, while other users' processes stay hidden. This is the host VM shell, not a simulated CSQuest command runner. Platform data and other users' home directories remain inaccessible, and system directories are read-only.

Run `sudo node tests/remote-terminal-vm.mjs` on the configured VM while Terminal is idle for the manual integration check. It launches two real ttyd sessions, verifies the initial root listing, prompt, system information, protected paths and persistence of a temporary practice file, then removes that file and stops its sessions. This check passed on the actual VM after installing the shell improvements; the existing remote authentication/session regression also passed.

## Browser stability and latency RCA (20 October 2026)

The old 256-task per-session limit caused Firefox content and utility process crashes. Seven saved crash annotations reported failure to create thread-pool threads; the aggregate cgroup recorded 543 denied task creations and zero out-of-memory kills. A fresh Firefox test reached 316 tasks with ordinary public-site tabs, exceeding the old cap. Raising memory alone would not address this failure. Firefox now permits 1,024 tasks under the bounded aggregate slice; memory limits remain unchanged.

The old slice also accumulated CPU throttling (544 periods, about 32.7 seconds cumulatively). The two-core VM now gives remote applications up to 1.5 cores with lower CPU weight than the platform. TigerVNC updates are limited to 30 fps, the browser viewport to 1,440 by 900, and noVNC uses quality level 5 / compression level 2. These reduce rendering and transport demand; they do not eliminate geographic network round-trip time or make VNC a video-streaming protocol. The WebSocket relay now pauses its upstream under backpressure instead of killing the session at a 2 MB frame backlog, and TCP input/output uses TCP_NODELAY.

The minimal installation lacked the system H.264 decoder library. The installer now includes `libavcodec60`; a real MP4 played in the isolated native browser after installation. Both browsers and terminal retain their sandbox, private-service/metadata restrictions and authentication requirements. No production remote debugging port is enabled.

The visible session addresses are `/workspace/browser` and `/workspace/terminal`. The existing `/remote.html?app=...` bookmarks normalize to those addresses; application labels may still identify Firefox. This is URL cleanup, not concealment from network monitoring.

Validation: authorization/session tests include clean routes and an 8 MB screen update with a paused client; Playwright checks new-tab launch, password verification, noVNC, desktop/mobile geometry, legacy URL normalization and tab-close cleanup. A separate temporary native-browser profile on the VM loaded YouTube and Stack Overflow under the actual service restrictions with zero task-limit denials or memory-kill events. Reddit returned its own HTTP 403/network-security block page in Firefox as well as curl; changing session resources cannot remove a destination site's access restriction. User browser profile data was not modified by the isolated test.

Final extended check kept multiple public-site tabs open and observed 364 tasks, zero task-limit denials and zero memory-kill events. The YouTube video page loaded without a browser crash but required sign-in to confirm the visitor was not a bot; playback time remained zero. This is a destination-side restriction, not successful YouTube video playback. The independent H.264 MP4 did play. Internal animation-frame medians were about 17 ms on the test pages; these are not measurements of the user's full network input-to-display latency. Temporary automation/debugging processes and profiles were removed after validation.

## Restart recovery and 4 GB Firefox limit

A later reported closure coincided exactly with a platform service restart: the service stopped at 17:09:01 UTC and restarted at 17:09:07 UTC. Its VNC connection closed at 17:09:01, followed by expiration of the old 30-second broker lease. Firefox peaked at about 1 GB, and neither the task-denial count nor memory-kill count increased. This was a transport/deployment interruption, not evidence of another resource crash.

Firefox now has the requested 4 GB memory ceiling and 2,048 tasks; the combined slice is capped at 5 GB and two cores, retaining lower CPU weight than the platform. Isolated temporary directories allow 512 MB in /tmp and 128 MB in /var/tmp, charged to the same session memory limit. Persistent home quotas are unchanged.

The browser UI retries temporary network/503 failures and recreates the noVNC transport without restarting Firefox. The broker uses connection-specific attachment tokens, a 20-second attachment heartbeat grace and a 90-second session lease. A replacement app process can reclaim a stale connection; stale detach requests cannot detach the replacement. Existing login/administrator checks still run, and permanent 401/403/404/410 errors end the viewer with a specific explanation. Explicit Stop and tab pagehide still request immediate process termination. Terminal PTYs do not promise recovery after disconnect.

Validation includes a new app server reconnecting to the same session, duplicate-connection protection, slow-client frame delivery, temporary HTTP 503 responses and a dropped noVNC connection. `sudo python3 tests/remote-session-resume-vm.py` checks actual VM caps and attachment replacement while Firefox is idle.
